# Self-contained verbose deploy script with per-step error handling

**Status:** released 2026-05-28 · v0.17.0 · error handling proven standalone (sqlcmd) + via apply
**Driver:** the generated deploy script is **silent** and has no per-step error
handling — only `SET XACT_ABORT ON` + a final implicit rollback. Redgate SQL
Compare's script is **self-managing**: it prints the exact phase it is in, gates
every batch (`IF @@ERROR <> 0 SET NOEXEC ON`) so the deploy aborts at the first
failure, and reports an overall succeeded/failed verdict (rolling back on
failure). This task makes DbDelta's default output match that robustness +
diagnostics.

This **reverses a previously-locked decision**: the 2026-05-25 parity audit
accepted omitting Redgate's `PRINT` / `IF @@ERROR` shell as a cosmetic
difference ("functionally equivalent under `SET XACT_ABORT ON`"). The owner now
prioritises parity, robustness, and diagnostics over the lean envelope.

## Decisions (from brainstorming)

- **Default, not opt-in.** The verbose + error-gated shell becomes the only
  output shape; the lean envelope is retired. All existing goldens re-baseline.
- **Full Redgate idiom.** Full `SET` preamble + `BEGIN TRANSACTION` + a per-batch
  `IF @@ERROR <> 0 SET NOEXEC ON` gate + a final
  `@Success` / `SET NOEXEC OFF` / `ROLLBACK` verdict block. One transaction, one
  rollback at the end, abort at the first failing step. No `xp_logevent`
  (Redgate-product telemetry).
- **Per-object/action `PRINT` granularity.** One phase label per operation
  (`Creating [s].[n]`, `Dropping [s].[n]`, `Altering [s].[n]`,
  `Rebuilding [s].[n]`, `Adding foreign keys on [s].[t]`, …). The **reason** on
  failure comes from SQL Server's native error message; the **verdict** is the
  final succeeded/failed line. No per-step "OK" line (unreliable across `GO`).

## Clarified semantics

"Handles the error at every step and rolls back" is realised as: **one**
transaction with a **per-step gate** that turns `NOEXEC ON` at the first error
(so every later batch is parsed-not-executed → the deploy stops at the failing
step) and a **single** transactional rollback in the final verdict block.
Per-step literal rollback inside one transaction would be wrong; the net effect
the owner wants — stop at the failing step, nothing half-applied, see which step
and why — is delivered by the gate + single rollback + native error message.

## Approach (chosen: centralized `DeploymentScriptWriter`)

A new `DeploymentScriptWriter` in `DbDelta.Core/ScriptGen/` owns batch emission.
Every emit site routes through `WriteBatch(label, body)`, which emits the
`PRINT` / `GO` / body / `GO` / gate / `GO` sequence. The per-object emitters
(`TableScriptEmitter`, etc.) are **unchanged** — they still return DDL strings;
only `ScriptGenerator`'s orchestration changes. Rejected: post-processing a lean
script by splitting on `GO` and inferring labels from SQL text (fragile);
pushing the verbose shell into each emitter (spreads the concern, breaks DRY).

## Components

### A. `DeploymentScriptWriter` + label scheme
- `WriteBatch(StringBuilder sb, string label, string body)` emits:
  ```
  PRINT N'<label, single-quotes doubled>';
  GO
  <body>
  GO
  IF @@ERROR <> 0 SET NOEXEC ON;
  GO
  ```
  (`PRINT` in its own batch so a `CREATE VIEW/FUNCTION/PROCEDURE/TRIGGER` body —
  which must be first in its batch — stays valid.)
- Label by `DifferenceStatus` + kind + identity: `OnlyInA → "Creating [s].[n]"`,
  `OnlyInB → "Dropping [s].[n]"`, `Different → "Altering [s].[n]"`
  (`"Rebuilding [s].[n]"` for an identity rebuild), foreign keys →
  `"Dropping foreign keys on [s].[t]"` / `"Adding foreign keys on [s].[t]"`,
  indexes → `"Creating indexes on [s].[t]"`, etc.

### B. Envelope (preamble + verdict footer)
Preamble (each a `GO`-separated batch):
`SET NUMERIC_ROUNDABORT OFF` · `SET ANSI_PADDING, ANSI_WARNINGS,
CONCAT_NULL_YIELDS_NULL, ARITHABORT, QUOTED_IDENTIFIER, ANSI_NULLS ON` ·
`SET XACT_ABORT ON` · `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` ·
`BEGIN TRANSACTION` · `IF @@ERROR <> 0 SET NOEXEC ON`.
Footer: `COMMIT TRANSACTION` · gate · then the verdict batch:
```
DECLARE @Success AS BIT
SET @Success = 1
SET NOEXEC OFF
IF (@Success = 1) PRINT 'The database update succeeded'
ELSE BEGIN
    IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION
    PRINT 'The database update failed'
END
GO
```
(When `NOEXEC` was turned on by an earlier error, `DECLARE`/`SET @Success` are
skipped → `@Success` is NULL → the `ELSE` branch rolls back + prints failed.)
Options respected: `DoNotOutputCommentHeader` (the `-- Generated by DbDelta`
header); `NoTransactions` (omit `BEGIN/COMMIT`; the verdict still rolls back only
`IF @@TRANCOUNT > 0`).

### C. Routing
All emit sites in `ScriptGenerator` — `DispatchEmit`/`EmitOneX`, the index loop,
the FK loop, the inbound-FK drop/re-add (#33), `EmitUsers`/`EmitRoles`/
`EmitPermissions` — go through `WriteBatch` with a computed label. The raw
`sb.AppendLine(ddl); sb.AppendLine("GO")` patterns are removed.

### D. `SqlExecutor` (the `apply` path) — drop the outer transaction
`SqlExecutor.ExecuteAsync` today wraps the whole script in **its own**
transaction. The new script is self-managing (its own `BEGIN`/`COMMIT`/
`ROLLBACK` + `NOEXEC`), so an outer wrapper conflicts (a script `ROLLBACK` would
unwind the wrapper; the wrapper's commit would then fail). Change `SqlExecutor`
to execute the GO-split batches **without** its own transaction, letting the
script govern transaction + rollback. It still GO-splits and reports
success/failure from batch exceptions. `dbdelta apply` and `SqlExecutorTests`
update accordingly.

## Testing

- **Golden re-baseline:** regenerate all ~29 ScriptGen goldens; review each diff
  to confirm it is the new shell (PRINT-per-batch + gate + verdict envelope), not
  a content regression. Add one golden showing the shell shape end to end.
- **Live success path** (reuse the LiveDb/`SqlExecutor` harness): generate →
  apply on a Testcontainers SQL Server → assert the script applies, prints
  `The database update succeeded`, and the re-compare converges.
- **Live failing-step path (the key correctness gate):** craft/inject a script
  whose middle step fails (e.g. an invalid statement), apply it, and assert: the
  failing step's phase `PRINT` is emitted, SQL Server's native error (the reason)
  is surfaced, execution stops at that step (NOEXEC), the transaction is rolled
  back (target unchanged), and the verdict is `The database update failed`. This
  proves the per-step error handling actually works.
- **Property:** every emitted batch is preceded by a `PRINT` and followed by the
  `IF @@ERROR <> 0 SET NOEXEC ON` gate; the verdict block is last.
- Re-run the parity / round-trip / CLI-acceptance suites that apply via
  `SqlExecutor` (its transaction change must not regress them).

## Risks

- **#1 — `IF @@ERROR <> 0 SET NOEXEC ON` after a `GO`.** `@@ERROR` resets between
  batches, so a gate in a batch *after* the statement's `GO` may not observe the
  prior batch's error. The real abort safety is `SET XACT_ABORT ON` (which dooms
  the transaction on any runtime error); the `NOEXEC` gate stops later batches
  from running. The **failing-step live test is the gate** that proves the abort
  + rollback + `failed` verdict actually happen; if the after-`GO` gate proves
  insufficient, the documented fallback is to rely on `XACT_ABORT` + a
  `@@TRANCOUNT`/`XACT_STATE()` check in the verdict (and keep the per-batch gate
  as defence-in-depth).
- **`SqlExecutor` losing its outer transaction** could regress the apply/parity/
  round-trip tests — all must be re-run green.
- **Large golden churn** — every golden changes; review is the labour.
