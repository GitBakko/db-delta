# #25 — DocFX API site + GitHub Pages (v1.0 RC)

**Status:** implemented 2026-05-27 · live at <https://gitbakko.github.io/db-delta/>
**Driver:** spec §1.x invariant 5 — "XML doc comments on all public types;
DocFX-rendered API site published to GitHub Pages." XML docs are already
emitted (`Directory.Build.props` → `GenerateDocumentationFile=true`); this task
adds the DocFX site + its automated publish to GitHub Pages.

## Scope

In scope: a DocFX documentation site = auto-generated **API reference** (from
the XML docs of the library projects) + a **minimal conceptual guide** (landing,
getting-started, CLI usage, comparison-options table), published to GitHub
Pages automatically on every push to `main`.

Out of scope (separate later milestones): WiX MSI installer; reworking the
existing internal design docs (`docs/00-06`, design-system); versioned/multi-
version docs; search-engine integration beyond DocFX's built-in.

## Approach (chosen: local dotnet tool + dedicated `docfx/` folder + separate workflow)

DocFX is pinned as a **local dotnet tool** (`.config/dotnet-tools.json`) so the
build is reproducible locally and in CI. All DocFX scaffolding lives in a
dedicated top-level `docfx/` folder, isolated from the existing `docs/` tree
(which holds internal design artifacts, parity, superpowers). A **separate**
`.github/workflows/docs.yml` builds and deploys — `ci.yml` is untouched and
stays green.

Rejected: installing DocFX ad-hoc in CI only (not locally reproducible);
scaffolding inside `docs/` (clashes with existing design docs).

## Components

### 1. Tooling — `.config/dotnet-tools.json`
A tool manifest pinning `docfx` (latest stable 2.x, ≥ 2.78). Usage:
`dotnet tool restore` then `dotnet docfx docfx/docfx.json`.

### 2. Folder layout (new `docfx/`)
```
docfx/
  docfx.json              # metadata (API from libs) + build (conceptual + api → _site)
  index.md                # landing page
  toc.yml                 # top nav: Articles | API
  articles/
    toc.yml               # Getting Started | CLI | Comparison Options
    getting-started.md
    cli.md
    comparison-options.md
  api/                     # GENERATED by `docfx metadata` (git-ignored)
  _site/                   # build OUTPUT (git-ignored)
```
`.gitignore` gains `docfx/api/` and `docfx/_site/`.

### 3. API reference — `docfx.json` `metadata`
Generates API YAML from the **four library projects**:
`src/DbDelta.Core`, `src/DbDelta.Shared`, `src/DbDelta.Persistence`,
`src/DbDelta.Providers.LiveDb`. Excludes the executables
`src/DbDelta.Cli` and `src/DbDelta.App.Avalonia` (apps, not a consumable API).
Consumes the already-emitted XML doc files. Output → `docfx/api/`.

`docfx.json` `build` section: conceptual `*.md` + generated `api/` + the
`toc.yml`s, DocFX `modern` template, output → `docfx/_site`. Global metadata:
`_appName: DbDelta`, `_enableSearch: true`.

### 4. Conceptual content (the minimal guide)
- `index.md` — what DbDelta is (open-source Redgate SQL Compare clone for SQL
  Server 2016+/Azure SQL; compares two live DBs, generates a dependency-ordered
  T-SQL deploy script), links to Getting Started + API.
- `articles/getting-started.md` — prerequisites (.NET 10 SDK), build from source
  (`dotnet build`), run the CLI, launch the Avalonia app.
- `articles/cli.md` — the four verbs: `compare`, `script`, `apply`, `report` —
  each with its options and a usage example, sourced from the actual
  `src/DbDelta.Cli/Commands/*Command.cs` definitions (verify flags at write time).
- `articles/comparison-options.md` — a table of the `ComparisonOptions` flags
  (from `src/DbDelta.Core/Options/ComparisonOptions.cs`) and the `Default` set,
  with a one-line meaning each.

### 5. Workflow — `.github/workflows/docs.yml`
```yaml
on:
  push: { branches: [ main ] }
  workflow_dispatch:
permissions: { pages: write, id-token: write, contents: read }
concurrency: { group: pages, cancel-in-progress: false }
```
One `build-and-deploy` job (ubuntu-latest): checkout → setup-dotnet
(global.json) → `dotnet tool restore` → `dotnet docfx docfx/docfx.json` →
`actions/configure-pages` → `actions/upload-pages-artifact` (path `docfx/_site`)
→ `actions/deploy-pages`. Independent of `ci.yml`.

### 6. GitHub Pages enablement (manual prerequisite)
Pages must be set to **Source: GitHub Actions** (Settings → Pages). Either the
maintainer toggles it, or (with repo-admin token) `gh api -X POST
repos/GitBakko/db-delta/pages -f build_type=workflow`. The first workflow run
cannot deploy until this is set; flagged at execution time.

## Verification

- **Local build clean:** `dotnet tool restore` then `dotnet docfx
  docfx/docfx.json` produces `docfx/_site` with **zero warnings**
  (`--warningsAsErrors` to catch broken xref / links). The API `api/` YAML is
  generated for all four libraries.
- **Spot-check rendered output:** `index.html`, an article page, and at least
  one API type page (e.g. `ComparisonEngine`, `ISchemaSource`) exist in
  `_site`.
- **CI:** the new `docs.yml` workflow run is green and the Pages URL serves the
  site. `ci.yml` remains green (unaffected).
- No unit tests — this is documentation; the gate is a clean DocFX build + a
  successful Pages deploy.

## Risks / notes

- **DocFX + .NET 10:** confirm the pinned DocFX version supports .NET 10
  metadata extraction; if metadata generation chokes on the SDK, fall back to
  pointing `metadata.src` at the built assemblies + XML rather than the
  `.csproj`. (Resolve during implementation.)
- **`warningsAsErrors`:** missing XML docs on some public members surface as
  warnings. If the public surface has gaps, either fill the docs or relax to
  warnings-not-errors for the first cut and track the gaps. (Decide during
  implementation based on the actual warning count.)
- **Pages enablement** is the one manual, out-of-band step.
