## Triage summary

### 🔴 Bugs to fix before v1.0 RC

1. **#33 — Sequence: ALTER vs DROP+CREATE.** When only the seed (or
   current value) differs and the data type / cycle / cache / min /
   max stay the same, emit `ALTER SEQUENCE [schema].[name] RESTART
   WITH n` instead of DROP+CREATE. Scenario 08 surfaces the real-world
   failure: any column with `DEFAULT NEXT VALUE FOR <sequence>` breaks
   under DROP. Owner: Core/ScriptGen, +1 emitter method, +golden test.

### 🟡 Design follow-ups for v0.14

1. **#31 — Column collation diff coverage.** Read `sys.columns.collation_name`
   into the `Column` record (or a sister record) and emit `COLLATE
   <name>` whenever the column's collation diverges from the database's
   default collation. Scenario 01 + 11 show Redgate emits explicit
   collations defensively. Today DbDelta would miss a column whose
   collation has been manually overridden.
2. **#32 — Identity rebuild: drop+re-add PK around the swap.** Mirror
   Redgate's pattern (drop PK before the rebuild, recreate after
   `sp_rename`) so that inbound FKs survive the rename. Fixture didn't
   exercise this — add a parity scenario in the v0.14 fixture (table
   B with FK → A, then identity-flip A).

### ✅ Cosmetic differences accepted (no action)

- **DbDelta emits `CREATE OR ALTER`** for view / function / procedure;
  Redgate emits bare `ALTER`. DbDelta is more defensive for re-runs.
  Lock as design choice.
- **DbDelta uses inline `[X_tmp]` naming** during table rebuilds;
  Redgate uses `[RG_Recovery_N_X]`. Both safe — DbDelta's is shorter.
- **DbDelta omits the Redgate-style `PRINT` / `IF @@ERROR <> 0 SET
  NOEXEC ON` shell** around every batch. Functionally equivalent
  under `SET XACT_ABORT ON`, which both emit at the top.
- **DbDelta keeps `[nvarchar](200)`** as `nvarchar(200)`; Redgate
  uses `[nvarchar] (200)` (bracketed type + whitespace). Identical
  to the parser.
- **DbDelta does not emit the deployment-log block** at the end
  (`xp_logevent` / monitor message). Out of scope for v1.

### Design differences locked in spec

- DbDelta's batch envelope (`SET XACT_ABORT ON; BEGIN TRAN; … COMMIT TRAN;`)
  is intentionally shorter than Redgate's six-`SET`-statement preamble.
  Reasoning: spec §3.1 already mandates `SET XACT_ABORT ON`; the rest
  is optional defence that bloats every script. Revisit if a real-world
  failure shows DbDelta missing a SET that Redgate caught.
