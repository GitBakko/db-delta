# DbDelta ↔ Redgate SQL Compare — parity run 2026-08-31 (v1.0.2)

The run the P3 backlog entry had been waiting on since 2026-05-28. The owner ran
`00-bootstrap` / `01-source` / `02-target` in SSMS and produced Redgate's
deployment script; DbDelta's half was generated from the same fixture and the
two were diffed statement by statement, then every claimed divergence was
re-derived by an independent pass that refused to take the first one on trust.

| Field | Value |
|-------|-------|
| Fixture | `tests/Fixtures/Parity/{00-bootstrap,01-source,02-target}.sql` — **21 scenarios** (+ 22 in `03-refusals.sql`, its own DB pair) |
| DbDelta version | `main` @ the commit that carries this file (v1.0.2 line) |

`scripts/parity/` is git-ignored: the two artifacts stay local, and the evidence
that has to survive is quoted here.

## Environmental caveat — read before reopening any row

The two scripts were **not** generated against the same server:

- Redgate's came from the owner's live host (`DbDeltaParity_Source` /
  `_Target`), whose default collation is `Latin1_General_CI_AS`.
- DbDelta's came from a Testcontainers `mssql/server:2022-latest` pair, whose
  default collation is `SQL_Latin1_General_CP1_CI_AS`.

The fixture declares **no** `COLLATE` anywhere and `00-bootstrap.sql` creates
both databases at the server default, so every collation-name difference in the
diff is that, and nothing else. What was checked instead — and what matters — is
that the `COLLATE` clause is **present on the same set of columns in both
scripts** (`Customer.Email`, `Region.Name`, `Documented.Note`,
`OrderItemTvp.Notes`, and no others). It is. The 2026-05-28 audit's
omit-when-default gap (#31) is closed.

## Headline

**Zero bugs. All 21 scenarios match, are accepted-cosmetic, or are the one
declared gap.** Both scripts were applied to fresh copies of the target in a
container and both printed `The database update succeeded`; a DbDelta re-compare
of source against the DbDelta-deployed target returned **Identical on all 30
objects**.

But the run did not come out clean, and the thing it found was **ours, in the
harness**: the first capture was generated without the target-side dependency
edges, so scenario 18 — the scenario whose entire purpose is drop ordering — was
measuring a fallback path the shipping product never takes. Fixed in the commit
that carries this file, and re-captured. Five more shapes were found where the
fixture happens to avoid a real failure; they are backlog entries, not parity
failures.

## The harness defect, and what it cost

`ParityFixtureTests` called:

```csharp
new ScriptGenerator().Generate(
    diff, selection: null, options: ComparisonOptions.Default,
    dependencies: source.Dependencies);        // ← dropDependencies omitted
```

Both shipping call sites pass it — `ScriptCommand.cs:93` and
`DeployScriptBuilder.cs:105`. Without it `ResolveDropOrder`
(`ScriptGenerator.cs:736-747`) falls through to `createOrder.Reverse()`, which is
kind rank inverted, not topology. With `DependencyResolver`'s ranks
(Table 3 < View 4 < Function 5, `DependencyResolver.cs:14-26`) that reversal
yields `fnLegacyTotal → vLegacyReport → LegacyStock`, which is exactly what the
first artifact contained.

| | first capture (fallback) | after the fix | Redgate |
|---|---|---|---|
| scenario 18 drop order | `fn → view → table` | `view → fn → table` | `view → fn → table` |

The fallback order is *legal* here — `vLegacyReport` merely calls
`fnLegacyTotal`, it is not schema-bound to it — which is why the test had been
green. Put `WITH SCHEMABINDING` on that view and the same fallback drops the
function first and dies on Msg 3729. So: the test that exists to prove drop
ordering was proving the wrong path, and `ScriptCommand`'s real drop-order path
had **no** end-to-end coverage at all. It does now.

## Risks the fixture does not reach

None of these is a parity failure — Redgate is unmeasured on most of them,
because the fixture never builds the shape. They are what the diff surfaced by
reading our side closely, and each is now a backlog entry.

- **R1 — CLOSED the same day (see docs/BACKLOG.md, P1; the surface turned out
  wider than this entry says — computed columns, an inline index's INCLUDE and a
  key column's DESC were being lost too, and an adversarial review of the fix
  opened three further entries) — a table type's PK / UNIQUE / CHECK are silently lost on rebuild, and
  the loss is undeclared.** `TableTypeUdt` (`TableTypeUdt.cs:12-15`) models only
  `Columns`; scenario 11's shape forces DROP + CREATE, so any key on the type
  goes and does not come back. The re-compare then reports **Identical**, so
  nothing surfaces it, and no second run repairs it. It is not a declared gap
  either: `UnexaminedReader`'s type filter excludes `'C'`, `'PK'`, `'UQ'` before
  `is_ms_shipped` is reached, and `UnexaminedCensus.Labels` has no key for it.
  A TVP with a primary key is the common case, not an exotic one.
- **R2 — no dependency edge exists for a type binding.** `EdgeKind` has seven
  members and none of them is one, and `sys.sql_expression_dependencies` records
  no row for a column bound to an alias type or a parameter bound to a table
  type, so the edge could not exist even if the enum had a member. `DROP TYPE`
  is therefore emitted naked, ahead of everything, and a bound column or TVP
  parameter gives Msg 3732. Reproduced on a throwaway pair with the fixture's own
  two types. Loud, not silent — but an alias type bound to a column is the normal
  reason to declare one.
- **R3 — the identity rebuild has no path for a schemabound module bound to the
  rebuilt table.** The rebuild restores inbound FKs, outbound FKs, indexes and
  triggers; `grep -i 'schemabind|3729|3732'` over `src/` returns six hits and all
  six are prose. `EmitRebuild`'s only refusal guard is the non-rowstore index
  check. A schemabound view over the rebuilt table gives Msg 3729 on the
  `DROP TABLE`, batch-aborting under `XACT_ABORT`, whole deploy rolled back and
  the target left divergent — a runtime failure, not a declared limit. The
  fixture separates the two shapes by construction (12 rebuilds `Order`; 16/17
  put `SCHEMABINDING` on tables that are plain CREATEs); on a real schema they
  co-occur constantly.
- **R4 — the inlined CHECK turns a legal schema into an internal error.**
  DbDelta emits `CONSTRAINT … CHECK` inside `CREATE TABLE`, which forces the
  table *after* the function, so the CHECK→function and function→table edges must
  form a DAG. `CHECK (dbo.fnRowCount() < 100)` where `fnRowCount` reads the same
  table is legal on a live server and is exactly that cycle. `DependencyResolver`
  throws `DependencyCycleException`; the **DROP** path catches it
  (`ScriptGenerator.cs:742`), the **CREATE** path at `:331-332` does not, and the
  CLI's only remaining handler is the generic one (`Program.cs:91`) → exit **99**
  with "open an issue", instead of the exit-30 declared refusal DbDelta already
  uses for three other unscriptable shapes. Redgate's trailing `ALTER TABLE` is
  immune by construction.
- **R5 — the batch-level error gate reads only the last statement's `@@ERROR`.**
  `SET XACT_ABORT ON` does not make every error batch-aborting. Measured on
  `mssql/server:2022-latest` 16.0.4265.3, inside `BEGIN TRANSACTION` with
  `XACT_ABORT ON`: a mid-batch `DROP TABLE dbo.NoSuchTable` (Msg 3701, Level 11)
  let the batch continue **and commit**; `EXEC sp_rename 'dbo.NoSuchObject', …`
  (Msg 15225, raised by `RAISERROR` from inside a system procedure) did the same,
  and the statement before it survived too. Both classes are reachable at
  `dbdelta-2026-08-31.sql:100/116` and `:101/117`. It is a **risk and not a bug**
  because in this script the survivor is immediately followed by an
  `ALTER TABLE … ADD CONSTRAINT` against the table the failed rename left
  missing — Msg 4902, which *is* aborting, so everything rolls back. Verified by
  running it. This is also why Redgate wraps `sp_addextendedproperty` in
  TRY/CATCH and nothing else: same non-aborting class.

## Cosmetics — recorded so a future byte-diff does not reopen them

Beyond the already-locked list (`CREATE OR ALTER`, `[X_tmp]` naming, trailing
`xp_logevent`, per-module `QUOTED_IDENTIFIER`, type-argument spacing):

| What | DbDelta | Redgate |
|---|---|---|
| `sp_rename` arity | `EXEC sp_rename '[dbo].[Invoice_tmp]', 'Invoice';` | `EXEC sp_rename N'…', N'Invoice', N'OBJECT'` |
| Index key direction | `([Email] ASC)` | `([Email])` |
| `PK_LegacyStock` | not dropped (the `DROP TABLE` takes it) | dropped explicitly first |
| CHECK placement | inline in `CREATE TABLE` | trailing `ALTER TABLE` |
| PRINT granularity | grouped; `:264` names no object | one per statement |

`sp_rename`'s omitted `@objtype` was checked rather than assumed: executed on
16.0.4265.3 it emits the usual *Caution: Changing any part of an object name…*
and succeeds, and a probe confirmed the parameter travels as NULL and still
resolves as an object. `Sql.L` (`Sql.cs:34-46`) doubles apostrophes here on
purpose, so a table named `O'Brien` still produces a parseable literal.

One internal inconsistency worth a decision, not a divergence: DbDelta's own
DROPs are not uniform — `IF EXISTS` at `:24` and `:30`, bare at `:36`, `:48`,
`:55`, `:246`, `:253`. The script is therefore neither uniformly fail-fast nor
re-runnable: a second run survives the first two and dies at `:36`. Pick one
policy.

## Refuted — claims that did not survive being re-run

- **"Redgate's finer gating leaves the transaction open when `NOEXEC` is on."**
  False, and the verdict block is *byte-identical in both scripts*
  (`dbdelta:274-281`, `redgate:423-430`), so it could never have been a
  difference between the tools. Run under `NOEXEC ON`: `SET @Success = 1` does
  not execute, `@Success` stays NULL, `NULL = 1` is not true, the `ELSE` branch
  fires — printed `The database update failed`, `@@TRANCOUNT` 0, rolled back.
  That is the point of the pattern.
- **"`ALTER SEQUENCE … RESTART WITH` moves only the next value, so scenario 08
  cannot converge."** Hypothesised because `ComparisonEngine.cs:264-272` compares
  `StartValue` read from `sys.sequences.start_value`. Measured: after the
  `RESTART`, `start_value` **and** `current_value` are both 100. The catalog
  column is updated; the comparison key is sound.
- Redgate emits two **inert** gates (`redgate:106`, `:306`) where
  `IF @@ERROR <> 0 SET NOEXEC ON` follows a `PRINT` rather than a DDL statement,
  so its 64-gates-to-35 advantage over DbDelta is slightly overstated.

## What this run changed in the repo

- `ParityFixtureTests` now passes `dropDependencies: target.Dependencies`, so it
  exercises the same generator inputs as `dbdelta script`.
- `DBDELTA_PARITY_DUMP` — set it to a path and the test writes its generated
  script there. Without it a clean checkout cannot reproduce the artifact this
  document diffs.
- Six backlog entries opened (R1–R5 plus the DROP-guard policy); the P3 parity
  entry is closed by this file. **R1 was closed the same day** — the reader,
  the model, the emitter and the comparison all learned a table type's keys,
  its computed columns, its INCLUDE lists and its key-column directions, and so
  did the diff pane, whose duplicate catalog query is gone. Reviewing that fix
  opened three more entries, two of them pre-existing defects it made visible:
  a memory-optimized table type scripted as a disk-based one, an alias type's
  name emitted without its schema, and a table's PK losing key-column
  direction the same way a table type's did.
